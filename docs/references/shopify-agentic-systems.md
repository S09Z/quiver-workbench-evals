## 1. practice ที่เขาทำ

### สถาปัตยกรรม

| practice | เขาทำยังไง |
|---|---|
| Just-in-time instructions | ส่งคำแนะนำกลับมาพร้อมผลของ tool ตอนที่ต้องใช้ แทนที่จะยัดทุกอย่างลง system prompt — prompt หลักสั้นลง แก้ง่ายขึ้น และ cache ได้ดีขึ้น |
| Modular tool design | เลี่ยง "Death by a Thousand Instructions" จำกัดขอบเขตของแต่ละ tool แทนการเขียนกรณียกเว้นลง prompt กลาง ประสบการณ์เขาคือเกิน ~50 tools แล้วคุมไม่อยู่ |
| Single-agent ก่อน multi-agent | ระบบ single-agent ธรรมดารับความซับซ้อนได้มากกว่าที่คิด — อย่ารีบแตกเป็นหลาย agent ตั้งแต่ต้น |

### การวัดผล (ส่วนที่เกี่ยวกับ repo นี้ตรง ๆ)

| practice | เขาทำยังไง |
|---|---|
| Ground Truth Set (GTX) แทน golden dataset | สุ่มบทสนทนาจริงตามการกระจายของ production ไม่ใช่คัดเคสสวย ๆ ที่เดาเอาเอง เพราะ dataset ที่คัดมาเองเดาทุกปฏิสัมพันธ์ที่เป็นไปได้ไม่ได้ |
| ให้คนหลายคน label แล้ววัดความเห็นตรงกัน | ผู้เชี่ยวชาญโปรดักต์อย่างน้อย 3 คน วัดกันด้วย Cohen's Kappa, Kendall Tau, Pearson |
| LLM-as-judge ต้องสอบเทียบกับคน | judge แยกตัวตามมิติที่จะวัด ไม่ใช่ตัวเดียวให้คะแนนรวม ไล่ปรับ prompt จนสหสัมพันธ์กับคนขึ้นจาก Cohen's Kappa 0.02 → 0.61 โดยที่คนกับคนเองอยู่ที่ 0.69 |
| User simulation | สร้าง simulator จำลองผู้ขาย เอาไว้ทดสอบ candidate หลายตัวเทียบกันก่อน deploy |
| N-stage gated rewards (ตอนเทรนด้วย GRPO) | ด่านแรกตรวจเชิงกระบวนการ (syntax, schema) ไม่ผ่านคือจบ ไม่ต้องเสียเงินเรียก judge ผ่านแล้วค่อยให้ judge ให้คะแนนเชิงความหมาย |
| เฝ้าระวัง reward hacking | opt-out hacking, ใช้ tag ผิดทาง, ละเมิด schema — เจอ failure mode ใหม่ก็อัปเดตทั้ง validator และ judge ตาม |

ประโยคที่เป็นหัวใจของบทความ: การทดสอบด้วยความรู้สึก (vibe testing) ไม่พอ
การประเมินต้องมีหลักและตรวจสอบทางสถิติได้

## 2. แล้ว repo นี้เอาอะไรมาใช้

| ของเขา | สถานะที่นี่ |
|---|---|
| GTX จาก distribution จริง | **ใช้แล้ว** — ตรงกับกฎ "ทุกครั้งที่โมเดลทำงานจริงพัง ให้แปลงเป็นเคสใหม่" เคสที่มาจากงานจริงมีน้ำหนักกว่าเคสที่ร่างไว้ตั้งแต่ต้น |
| ด่าน procedural ก่อนด่าน semantic | **ใช้แล้ว** — กลไก Computable/Holdout ใน [MODEL_EVAL.md](../../MODEL_EVAL.md) §6 คือด่านแรกแบบเดียวกัน ผิดเลขคือผิด ไม่ต้องเถียงเรื่องคุณภาพงานเขียน |
| judge แยกตัวตามมิติ | **ใช้แล้วในรูปของ rubric** — เราให้คะแนนแยกเกณฑ์ 0–2 อยู่แล้ว ไม่ใช่คะแนนรวมก้อนเดียว |
| ให้คนหลายคน label + วัด Kappa | **ยังไม่ทำ** — ที่นี่มีคนให้คะแนนคนเดียว ทางที่ใกล้เคียงที่สุดคือให้คะแนนเคสเดิมซ้ำคนละวันแล้วดูว่าตัวเองให้ตรงเดิมไหม ถ้าไม่ตรง แปลว่าเกณฑ์ยังคลุมเครือ ต้องแก้เกณฑ์ ไม่ใช่แก้คนให้คะแนน |
| LLM-as-judge | **ยังไม่ทำ โดยตั้งใจ** — ดู [CLAUDE.md](../../CLAUDE.md) หัวข้อการตัดสินใจที่ตกลงกันไว้แล้ว และ MODEL_EVAL.md §15 ต้องอ่านคำตอบเองครบ 30–40 อันก่อน ถึงตอนนั้นค่อยเอาวิธีสอบเทียบของ Shopify มาใช้ ประเด็นสำคัญคือ **ความเห็นตรงกันของคนคือเพดานของ judge** — judge ที่ดีกว่าคนไม่มีอยู่จริงในวิธีวัดแบบนี้ |
| User simulation | **ยังไม่ทำ** — งานที่นี่เป็น prompt เดี่ยว ไม่ใช่บทสนทนาหลายตา ยังไม่มีอะไรให้จำลอง |
| GRPO / reward hacking | **ไม่ทำ** — คนละสเกล Sidekick รันที่ 72 ล้านชิ้นต่อวัน ที่นี่รันหลักสิบ |
| JIT instructions / tool design | **ไม่เกี่ยวตอนนี้** — harness ยิง prompt ตรง ไม่มี tool ให้โมเดลเรียก ถ้าวันหนึ่งขยายเป็น agent ค่อยกลับมาอ่านหัวข้อนี้ |

## 3. สิ่งที่ยืนยันการตัดสินใจเดิม

บทความนี้ไม่ได้ทำให้ต้องเปลี่ยนอะไรใน repo — มันยืนยันสองข้อที่ตกลงกันไว้แล้ว

1. **ให้คะแนนด้วยมือก่อน** Shopify เองก็เริ่มจากคนให้ label แล้วค่อยสอบเทียบ judge
   ตามหลัง ไม่ได้เริ่มจาก judge
2. **เคสต้องมาจากของจริง** ไม่ใช่ golden dataset ที่คัดมาเอง

สิ่งที่ยืมมาใช้ได้ทันทีคือกฎเรียงลำดับด่าน — **เช็คสิ่งที่ตรวจได้เชิงกลไกก่อนเสมอ
ก่อนจะไปตัดสินคุณภาพ** ถ้าคำตอบมั่วตัวเลขหรืออ้างแหล่งที่ไม่มีอยู่จริง จบตั้งแต่ด่านแรก
ไม่ต้องเสียเวลาอ่านว่าวิเคราะห์ลึกไหม
